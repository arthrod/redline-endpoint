# Debugging Word "Unreadable Content" Warning

## Problem

When opening DOCX files generated by Docxodus/WmlComparer, Microsoft Word may display:
> "Word found unreadable content in [filename]. Do you want to recover the contents of this document?"

The document works after clicking "Yes", but the warning is undesirable.

---

## Root Cause Analysis (2026-01-15)

### Investigation Summary

After thorough analysis of the Docxodus library (v5.4.0) and the original documents, we found:

1. **Source documents are clean** - Original and modified DOCX files have standard `rIdN` format relationship IDs and relative paths
2. **GUID-style IDs are valid** - Per OOXML spec, relationship IDs just need to be unique within their scope
3. **Absolute paths are valid** - OOXML allows both `/word/filename.xml` and `filename.xml` in relationships
4. **pt14 namespace is the real issue** - PowerTools internal namespace should be cleaned

### Critical Bug Found in Previous Implementation

The previous `FixRelationshipsXml` method had a **critical bug**:

```csharp
// BUG: This changes the ID but does NOT update references in document content!
if (!idAttr.Value.StartsWith("rId"))
{
    idAttr.Value = $"rId{nextId++}";  // Changes R76e2e2db... to rId8
}
```

When relationship IDs are changed (e.g., `R76e2e2db410345d5` → `rId8`), all references in document.xml and other parts like:
```xml
<w:footnotePr r:id="R76e2e2db410345d5"/>
```

Would become broken references, **causing** the "unreadable content" warning instead of fixing it!

---

## Attempted Solutions

### Attempt 1: Remove pt14 Namespace Only
- **Status:** ✅ Correct approach
- Removes `pt14:Unid` and `pt14:Status` attributes
- Removes `xmlns:pt14="..."` namespace declaration
- Removes `pt14` from `mc:Ignorable` attribute

### Attempt 2: Fix Relationships Using OpenXML SDK
- **Status:** ❌ Not possible (IPackageFeature is internal in SDK 3.x)

### Attempt 3: Fix Relationships Using ZipArchive
- **Status:** ❌ BUGGY - breaks document by changing IDs without updating references
- This approach was **removed** as it was likely causing the issue, not fixing it

---

## Current Solution (Simplified)

The current implementation only removes the pt14 namespace, which is the only known issue that could cause Word warnings:

```csharp
private static byte[] CleanPowerToolsNamespace(byte[] docBytes)
{
    // Only clean pt14 namespace - don't touch relationships!
    // GUID-style relationship IDs are valid per OOXML spec.
}
```

**Key insight:** If the raw Docxodus output (before any cleaning) opens in Word without warnings, then the previous "cleaning" was actually breaking the document. Test the raw output first before adding any cleaning logic.

## Diagnostic Commands

```bash
# Unpack DOCX
mkdir -p /tmp/unpacked && unzip -o -q document.docx -d /tmp/unpacked

# Check for pt14 references
grep -r "pt14" /tmp/unpacked/

# View relationships (should have valid IDs and paths)
python3 -c "import xml.dom.minidom; print(xml.dom.minidom.parse('/tmp/unpacked/word/_rels/document.xml.rels').toprettyxml())"

# Run diagnostic script
python3 diagnose.py output.docx
```
